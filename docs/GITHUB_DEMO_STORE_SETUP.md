# GitHub 테스트 저장소 설정

이 기능은 자체 서버 구축 전 기획·화면 검증을 위한 합성 데이터 저장 기능입니다. 실제 개인정보나 실제 교육평가 응답을 저장하지 않습니다.

## 저장 구조

- 코드: `main` 브랜치
- 합성 테스트 데이터: `demo-data` 브랜치의 `tap-demo/v1/`
- 기업 레지스트리: `companies/{company_id}/company.json`
- 기업별 프로젝트 정의: `companies/{company_id}/projects/{project_id}.json`
- 기업별 완료검사 스냅샷: `companies/{company_id}/submissions/{project_id}/{participant_key}.json`
- 참여자용 프로젝트 탐색 인덱스: `project-index/{project_id}.json`
- 참여자 식별: 원문 ID가 아닌 프로젝트별 해시 키
- 저장 시점: 문항별 저장이 아닌 교육 전·후 검사 완료 시점

데이터 커밋을 코드 브랜치와 분리하므로 검사 저장으로 Streamlit 앱이 다시 배포되지 않습니다.

## 1. GitHub 토큰 생성

GitHub의 Fine-grained personal access token을 다음과 같이 생성합니다.

1. 대상 저장소: `skytree96-cmyk/KMA_TAB_v2`만 선택
2. Repository permissions: `Contents`의 `Read and write`만 허용
3. 짧은 만료기간 설정

`Actions`, `Administration`, 다른 저장소 권한은 필요하지 않습니다.

## 2. Streamlit Secrets 등록

Streamlit Community Cloud의 앱 설정에서 **Secrets**에 다음 내용을 등록합니다. 토큰은 코드나 GitHub 파일에 커밋하지 않습니다.

```toml
[github_demo_store]
enabled = true
repository = "skytree96-cmyk/KMA_TAB_v2"
branch = "demo-data"
token = "github_pat_발급값"
participant_hash_salt = "충분히-길고-임의적인-테스트용-문자열"
participant_access_code = "참여자에게-전달할-기획검증-접속코드"
report_preview_code = "교육담당자에게만-전달할-별도-리포트미리보기-코드"
```

`participant_access_code`는 참여자의 완료 결과 저장과 교육 전 결과 조회를 막는 기획검증용 공유코드입니다. 공개 합성 데모의 KMA 기업 승인·거절에는 별도 비밀번호나 Secret을 사용하지 않습니다. 화면에서 합성데이터 신청임을 명시적으로 확인한 뒤 처리하며, 실제 쓰기는 앱 서버에 설정된 저장소 토큰으로만 가능합니다.

사업자등록번호는 비밀 salt와 HMAC 처리해 `company_id`와 회사 확인값을 만들며 원문은 저장하지 않습니다. 동일 사업자등록번호의 `company_id`는 표시 회사명이 바뀌어도 유지됩니다. salt를 바꾸면 기존 기업키와 참여자 연결키를 다시 만들 수 없으므로 기획검증 기간 중에는 동일 값을 유지하세요.

현재 두 입력값은 합성데이터 기획검증판의 기업 범위를 구분하는 장치이며 실제 관리자 인증이 아닙니다. 사업자등록번호는 공개될 수 있는 식별자이므로 실제 회원사 데이터에서는 계정 로그인·RBAC·MFA로 교체해야 합니다.

모든 Secrets 값은 저장소 파일에 커밋하지 않습니다. 참여자 코드가 없거나 일치하지 않아도 현재 브라우저 세션과 기준파일(JSON) 흐름은 계속 사용할 수 있습니다.

공유 접속코드는 사용자별 인증이 아닙니다. 합성 테스트에서도 교육 참여자 ID는 이름·사번·순번이 아니라 참여자별로 무작위 배정한 추측하기 어려운 가명 코드를 사용하세요. 실제 운영에서는 참여자별 만료형 이어하기 토큰과 서버 인증으로 교체합니다.

`report_preview_code`는 N<5 표본의 전·후 N각형을 **화면에서만** 확인하는 교육담당자용 기획검증 코드입니다. 참여자 접속코드로 대체할 수 없으며, 쓰기용 GitHub 토큰은 요구하지 않습니다. 이 공유코드 방식은 데모 접근 마찰을 위한 장치일 뿐 사용자별 인증·권한 관리가 아닙니다. 자체 서버 전환 시에는 강한 관리자 인증과 역할 기반 접근제어(RBAC)로 반드시 교체합니다.

KMA 대시보드의 참여 기업 목록에는 회사명, 승인상태, 신청·검토시각, 프로젝트 수, 교육 전/후 완료현황만 표시됩니다. 사업자등록번호 원문과 관리자 개인 정보는 저장·표시하지 않습니다. 따라서 현재 `관리자 범위`는 관리자 개인 목록이 아니라 기업마다 하나씩 부여한 회사 단위 범위를 뜻합니다.

저장 후 앱을 재시작하고 관리자 대시보드의 `GitHub 테스트 저장소 연결됨` 표시를 확인합니다.

## 3. 테스트 순서

1. 교육담당자 화면에서 회사명·사업자등록번호로 기업 참여 요청
2. KMA 대시보드에서 합성데이터 신청임을 확인하고 신청 승인
3. 교육담당자가 같은 회사명·사업자등록번호로 승인 상태 확인
4. 교육평가 프로젝트 생성 및 기업별 GitHub 경로 게시 확인
5. 다른 브라우저에서 프로젝트 코드로 기업 범위가 포함된 프로젝트 불러오기
6. 무작위 가명 교육 참여자 ID로 교육 전/후 검사 완료
7. KMA 대시보드의 참여 기업 목록과 회사별 완료 현황 확인

## 운영 전환 주의

GitHub 저장은 트랜잭션·개인정보 삭제·대량 동시 제출에 적합한 운영 DB가 아닙니다. 자체 서버 전환 시 `database/production_schema.sql` 기반 PostgreSQL 저장소로 교체하고, 현재 GitHub 저장 어댑터는 제거하거나 합성 데이터 전용으로 유지합니다.
