# TAP 기업 범위·권한 설계 v1

## 목적

LXP의 역할별 홈·운영 메뉴 분리 방식을 TAP의 평가 프로젝트 운영에 적용한다. 핵심은 메뉴 수 확대가 아니라, 여러 기업과 여러 관리자가 동시에 사용해도 데이터가 섞이지 않는 **기업 범위(tenant scope)** 확립이다.

## 기업 신청·승인

- 교육담당자 입력: 회사명, 사업자등록번호 두 항목
- 저장값: 비가역 HMAC으로 만든 `company_id`, 표시용 `company_name`, 승인상태와 시각
- 미저장값: 사업자등록번호 원문
- 동일 사업자등록번호는 회사명 표기가 달라져도 같은 `company_id`로 연결
- 상태: `승인 대기 → 승인 완료` 또는 `승인 거절`

미등록 기업은 참여 요청만 저장되고 프로젝트·대시보드·조직 리포트는 열리지 않는다. KMA 시스템 운영자가 KMA 대시보드에서 합성데이터 신청임을 명시적으로 확인한 뒤 승인한다. 공개 데모에서는 별도 승인 비밀번호를 사용하지 않으며, 승인상태가 없는 기존 합성 레지스트리는 호환을 위해 승인 완료로 해석한다.

## 코드와 인증 경계

- 참여자 접속코드: 배포된 프로젝트 검사 참여
- 리포트 미리보기 코드: N<5 기획검증 결과의 화면 미리보기에만 사용
- 저장값: 필요한 용도별 HMAC digest만 저장
- 미저장값: 사업자등록번호·접속코드 원문

회사명과 사업자등록번호만 사용하는 현재 흐름은 **합성데이터 기획검증용 기업 범위 구분**이며 관리자 개인 인증이 아니다. 실제 운영 전환 시에는 관리자별 계정·MFA·역할 기반 접근제어(RBAC)·감사로그로 교체한다.

## KMA 참여 기업 목록

KMA 대시보드는 등록 요청이 한 번이라도 저장된 기업을 회사 단위로 목록화한다.

- 표시: 회사명, 승인상태, 신청·검토시각, 프로젝트 수, 교육 전/후 완료현황
- 미표시: 사업자등록번호 원문, 관리자 개인 정보
- 조치: 승인 대기 기업의 승인 또는 거절과 선택적 검토 메모 기록

현재의 `관리자 범위`는 기업마다 하나인 회사 범위를 뜻하며, 관리자 개인을 식별하는 계정 목록이 아니다. 여러 담당자를 개인별로 구분하는 기능은 자체 DB·로그인·역할 배정·감사로그를 도입하는 후속 단계에서 제공한다.

## 역할 구조

| 역할 | 기본 범위 | 주요 기능 |
|---|---|---|
| 참여자 | 본인 | 해야 할 검사, 교육 전/후 검사, 내 결과 |
| 기업 프로젝트 관리자 | 소속 기업 | 프로젝트·일정·참여자·진행현황·조직 리포트 |
| 기업 리포트 열람자 | 소속 기업, 읽기 전용 | 5명 이상 조직 집계와 승인된 다운로드 |
| KMA 측정 관리자 | 측정도구 | 역량·문항·버전·채점·리포트 템플릿 |
| KMA 시스템 운영자 | 전체 운영 | 기업·계정·권한·저장소·감사·보존/삭제 |

KMA 시스템 운영자는 기본적으로 개인 응답과 개인 점수를 열람하지 않는다.

## 프로젝트 허브

기업 관리자는 프로젝트 목록에서 하나를 선택해 다음 탭으로 운영한다.

1. 개요
2. 설정
3. 참여자·코드
4. 진행현황
5. 교육 전/후 리포트
6. 내보내기
7. 변경이력

프로젝트 상태는 `초안 → 게시 → 교육 전 진행 → 교육 중 적용 → 교육 후 진행 → 리포트 공개 → 보관` 순으로 관리한다.

## 저장 범위

- 신규 프로젝트·제출: `company_id`가 포함된 기업별 경로
- 관리자 대시보드·리포트: 활성 `company_id`로 필터한 결과만 사용
- 참여자: 프로젝트 코드로 프로젝트를 찾되, 저장된 `company_id` 범위를 자동 복원
- 레거시 데이터: 기업 범위가 없는 기존 합성 데이터는 레거시로만 읽고 신규 기업 집계에 자동 혼합하지 않음

현재 GitHub `demo-data`는 합성 데이터용 기획검증 저장소다. 실제 운영에서는 자체 서버 DB의 `tenant`, `user`, `role_assignment`, `project`, `assessment_assignment`, `submission`, `report_access`, `audit_event` 구조로 이전한다.

## 단계별 적용

1. 역할별 홈, 기업 참여 요청·KMA 승인, 기업별 프로젝트 필터
2. 리포트 열람자, 참여자 배정, 프로젝트 변경이력
3. 자체 DB, 실제 로그인/RBAC, SSO, 감사로그, 보존·삭제 정책
